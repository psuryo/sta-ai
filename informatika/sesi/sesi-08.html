Materi — OAuth2

Otorisasi Terdelegasi, Bukan Sekadar Login

Di Backend Programming, Anda sudah memakai JWT untuk menandai pengguna yang sudah login. OAuth2 menjawab pertanyaan yang berbeda: bagaimana sebuah aplikasi mendapat izin terbatas untuk bertindak atas nama pengguna di layanan lain, tanpa pernah memegang password pengguna. OAuth2 sendiri adalah kerangka otorisasi. Untuk membuktikan identitas pengguna, OAuth2 biasanya dilengkapi OpenID Connect (OIDC) di atasnya.

Resource Owner
Pengguna yang memiliki data dan memberi izin.
Client
Aplikasi yang meminta izin. Pada lab 07, ini server GraphQL Anda.
Authorization Server
Pihak yang mengautentikasi pengguna dan menerbitkan token. Pada lab 07, ini GitHub.
Resource Server
API yang dilindungi dan menerima access token.

Scope: Izin yang Sempit

Token OAuth2 membawa scope, yaitu daftar tindakan yang diizinkan (misalnya read:products atau write:orders). Prinsipnya least privilege: minta dan berikan izin sesempit mungkin, sehingga token yang bocor tidak otomatis membuka seluruh sistem.

Materi — API Key Management

API Key: Sederhana, Tapi Sering Salah Kelola

API key mengidentifikasi aplikasi pemanggil, bukan pengguna. Cocok untuk akses sederhana antar sistem atau untuk pembatasan kuota, tetapi pengelolaannya perlu disiplin:

  • Simpan sebagai hash di server, seperti password. Tampilkan key penuh hanya sekali saat dibuat.
  • Kirim lewat header (mis. X-API-Key), bukan lewat URL yang bisa tercatat di log.
  • Jangan ditanam di kode frontend atau repository publik. Key yang bocor di GitHub adalah insiden keamanan klasik.
  • Beri batasan: scope, rate limit, dan masa berlaku agar kerusakan terbatas jika bocor.
  • Siapkan rotasi dan pencabutan: satu key bisa dimatikan tanpa mengganggu key lain.
Materi — mTLS

Saat Kedua Pihak Harus Membuktikan Identitas

Pada TLS biasa (HTTPS), hanya server yang menunjukkan sertifikat; klien memverifikasi server. Pada mutual TLS (mTLS), klien juga menunjukkan sertifikat, sehingga server hanya menerima koneksi dari klien yang sertifikatnya ia percayai.

1. Klien menghubungi server

Handshake TLS dimulai seperti biasa.

2. Server menunjukkan sertifikatnya

Klien memverifikasinya terhadap Certificate Authority (CA) yang dipercaya.

3. Server meminta sertifikat klien

Inilah perbedaan utama dari TLS biasa.

4. Klien menunjukkan sertifikat dan server memverifikasinya

Hanya setelah kedua sisi terverifikasi, koneksi dibuka.

mTLS umum dipakai untuk komunikasi antar microservice yang sensitif (gRPC mendukungnya secara native), tetapi menambah beban operasional: penerbitan, distribusi, dan rotasi sertifikat untuk setiap service.

Batasan Praktis di Proyek Ini

Platform hosting gratis seperti Render dan Vercel umumnya mengakhiri TLS di sisi platform, sehingga mTLS antar service sulit diterapkan penuh di sana. Kelompok yang ingin menerapkan mTLS sebaiknya mendemonstrasikannya di lingkungan Docker Compose (lab 08/13), atau memilih OAuth2 dan API key sebagai mekanisme keamanan lanjutan utama dan membahas mTLS sebagai rancangan.

Syarat Arsitektur Minimal

  • 2 service terpisah atau lebih.
  • 1 mekanisme komunikasi asinkron (message queue/event).
  • 1 penerapan keamanan lanjutan (OAuth2/API key/mTLS), materi sesi ini.
  • 1 protokol selain REST (GraphQL atau gRPC), dipilih sesuai kebutuhan sistem.

Tidak ada protokol yang diwajibkan secara spesifik, tetapi Anda wajib menulis justifikasi pilihan di laporan dengan mengacu pada kerangka keputusan di sesi 7 (konsumen API, variasi data, kebutuhan performa, sistem legacy).

Diskusi Kelas
Aktivitas Kelompok

Dalam kelompok proyek Anda, tentukan sekarang: komponen mana saja di sistem Anda, dan mekanisme keamanan apa yang cocok untuk masing-masing (pengguna ke sistem, antar service, partner eksternal)? Siapkan satu tabel sederhana "komponen → mekanisme → alasan" untuk dipresentasikan singkat di akhir sesi.

Rangkuman
  • OAuth2 adalah kerangka otorisasi terdelegasi. Authorization Code + PKCE untuk pengguna, Client Credentials untuk antar service.
  • API key mengidentifikasi aplikasi, bukan pengguna, dan butuh pengelolaan disiplin (hash, header, rotasi, batasan).
  • mTLS membuat kedua ujung koneksi saling membuktikan identitas, dengan biaya operasional sertifikat yang lebih besar.
  • Pilih mekanisme berdasarkan pertanyaan yang ingin dijawab, dan gabungkan bila perlu.
  • Proyek lintas mata kuliah dimulai sekarang: bangun satu sistem, uji satu sistem milik kelompok lain, tulis satu laporan gabungan.
