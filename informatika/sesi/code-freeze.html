Prosedur Code Freeze

Cara memastikan sistem yang diuji kelompok penguji benar-benar stabil: apa yang dibekukan, bukti apa yang diserahkan, bagaimana serah-terima disahkan, dan bagaimana perubahan setelahnya dikendalikan.

1 — Peran

Siapa Berbuat Apa

Code freeze tidak diawasi dosen sendirian. Kelompok penguji, yang paling berkepentingan agar sistem stabil, ikut menjadi pengawas lewat gerbang serah-terima.

Kelompok Pembangun
  • Menyiapkan paket serah-terima
  • Menandai freeze di Git
  • Menyediakan lingkungan uji yang stabil
  • Memperbaiki bug hanya lewat issue
Kelompok Penguji
  • Menjalankan smoke test serah-terima
  • Menerima atau menolak freeze (tertulis)
  • Melaporkan bug sebagai issue
  • Retest setelah perbaikan
Dosen
  • Menetapkan batas waktu
  • Memeriksa tag dan riwayat commit
  • Menjadi penengah jika ada sengketa
  • Memutuskan konsekuensi keterlambatan
2 — Lingkup

Apa yang Dibekukan

Mulai hari freeze tidak ada perubahan fitur atau arsitektur. Empat hal berikut dibekukan:

  1. Kode: seluruh source code yang berjalan di lingkungan uji.
  2. Kontrak API: OpenAPI, file .proto, atau skema GraphQL.
  3. URL deployment: alamat yang diberikan kepada penguji tidak berganti.
  4. Skema database: struktur tabel yang dipakai sistem.
Perubahan setelah freezeBoleh?Syarat
Perbaikan bug dari laporan pengujiBolehMerujuk nomor issue; dikerjakan di branch freeze
Perbaikan atau penjelasan dokumentasi yang diminta pengujiBolehDicatat di issue; tidak mengubah perilaku sistem
Fitur baru atau perubahan arsitekturTidakBoleh dikerjakan di branch lain, tetapi tidak masuk lingkungan uji
Perubahan kontrak API (endpoint, field, skema)TidakKecuali sebagai perbaikan bug yang disetujui penguji lewat issue
Perubahan skema databaseTidakKecuali dibutuhkan langsung oleh perbaikan bug dan dicatat di issue
3 — Bukti di Git

Menandai Freeze di Git

Titik freeze ditandai dengan tag, sehingga bisa diperiksa kapan saja tanpa mengandalkan klaim lisan.

Langkah untuk kelompok pembangun

# 1. tandai kondisi kode pada hari freeze git tag -a v1.0-freeze -m "Code freeze sesi 12" git push origin v1.0-freeze # 2. buat branch khusus dari tag itu, untuk lingkungan uji git checkout -b freeze v1.0-freeze git push origin freeze

Atur platform deployment (Render, Vercel, atau sejenisnya) agar lingkungan uji dibangun dari branch freeze, bukan dari main. Dengan begitu, pengembangan lanjutan di main tidak ikut mengubah sistem yang sedang diuji. Pastikan platform yang Anda pakai memang mendukung pemilihan branch untuk deployment.

Buat juga GitHub Release dari tag v1.0-freeze dan lampirkan paket serah-terima (bagian 4) di deskripsinya, sebagai satu tempat rujukan resmi.

Catatan

Repositori privat perlu menambahkan dosen dan kelompok penguji sebagai collaborator dengan akses baca agar tag dan riwayat commit bisa diperiksa. Fitur proteksi branch tertentu bergantung pada paket akun GitHub, jadi jangan menjadikannya satu-satunya mekanisme: riwayat commit dan issue tetap menjadi sumber pemeriksaan utama.

4 — Serah-terima

Paket Serah-terima

Pada hari freeze, pembangun menyerahkan satu paket berisi:

  • Spesifikasi OpenAPI lengkap untuk endpoint REST
  • Skema GraphQL (dengan contoh query/mutation) atau file .proto, sesuai protokol non-REST yang dipilih
  • README: cara mengakses sistem, daftar endpoint, cara autentikasi
  • Daftar environment variable yang dibutuhkan penguji, dengan placeholder (bukan secret asli)
  • URL deployment yang stabil
  • Nama tag dan hash commit yang dibekukan (v1.0-freeze)
  • Kredensial uji: akun atau API key khusus penguji, terpisah dari yang dipakai pembangun
  • Data uji: skrip seed dan cara mereset data ke kondisi awal
  • Keterbatasan yang diketahui: misalnya layanan gratis yang "tertidur" setelah idle sehingga request pertama lambat
  • Kontak: satu penanggung jawab teknis di kelompok pembangun
5 — Pengesahan

Gerbang Serah-terima

Freeze baru dianggap sah setelah kelompok penguji menjalankan smoke test 15–30 menit dan memutuskan menerima. Smoke test bukan pengujian mendalam; ia hanya memastikan sistem cukup siap untuk diuji.

Formulir Serah-terima Code Freeze
Kelompok pembangun / penguji: ______ / ______
Tag & hash commit: ______________________
☐ Kelima item dokumentasi inti tersedia dan terbaca
☐ URL deployment menjawab (request pertama boleh lambat bila layanan "tertidur")
☐ Contoh endpoint di README berfungsi sesuai yang tertulis
☐ Autentikasi (token/API key) bekerja dengan kredensial uji
☐ Data uji bisa direset dengan cara yang dijelaskan
Keputusan: ☐ DITERIMA   ☐ DITOLAK
Alasan (jika ditolak): ______________________
Nama penguji & waktu: ______________________

Jika ditolak, pembangun memperbaiki kekurangan paket dan menyerahkan ulang. Batas waktu perbaikan ditetapkan dosen (usulan awal: 2 hari). Jika kedua kelompok berselisih soal penolakan, dosen menjadi penengah.

Simpan formulir yang sudah diisi (foto atau salinan digital) dan lampirkan ke GitHub Release atau kumpulkan ke dosen.

6 — Kontrol Perubahan

Kontrol Perubahan Setelah Freeze

Langkah 1

Penguji membuka issue

Setiap temuan ditulis sebagai issue di repositori pembangun, memakai templat di bawah.

Langkah 2

Pembangun memperbaiki di branch freeze

Perbaikan lewat commit atau pull request yang menyebut nomor issue (misalnya "Fix #7: validasi stok negatif").

Langkah 3

Deploy ulang

Lingkungan uji diperbarui dari branch freeze. Pembangun memberi tahu penguji.

Langkah 4

Penguji retest dan menutup issue

Issue ditutup hanya oleh penguji setelah perbaikan terbukti. Retest ini yang dinilai di komponen "Retest & verifikasi".

Aturan Inti

Setiap commit di branch freeze setelah tag harus merujuk satu issue. Commit tanpa issue dianggap pelanggaran freeze.

Templat issue bug

Judul: [singkat dan spesifik] Tingkat keparahan: Kritis / Tinggi / Sedang / Rendah Endpoint / komponen: [mis. POST /bookings] Langkah reproduksi: 1. ... 2. ... Hasil yang diharapkan: ... Hasil aktual: ... Bukti: [screenshot, respons, atau log] Lingkungan: [URL + hash commit yang diuji]
7 — Lingkungan

Lingkungan Uji & Uji Beban

  • Pisahkan lingkungan. URL untuk penguji harus stabil dan dibangun dari branch freeze. Pembangun bebas bereksperimen di lingkungan lain.
  • Pisahkan data. Data uji penguji dipisahkan dari data demo, dan bisa direset lewat skrip seed. Uji beban atau uji kegagalan tidak boleh merusak data demo.
  • Koordinasikan rate limiting. Gateway dari lab 08 membatasi request (mis. 20 per 10 detik). Uji beban akan langsung terkena batas ini. Pembangun menyediakan cara melonggarkannya untuk penguji, misalnya API key khusus penguji dengan batas lebih tinggi di lingkungan uji. Batas yang dilonggarkan dicatat di paket serah-terima.
  • Sepakati jadwal dan batas uji beban. Layanan gratis punya batas penggunaan dan bisa melambat atau memblokir jika kelebihan beban. Penguji dan pembangun menyepakati waktu dan skala uji beban sebelum dijalankan.
  • Cantumkan keterbatasan platform di README (misalnya layanan yang "tertidur" setelah idle), agar penguji tidak menyangka sistemnya rusak.
8 — Verifikasi

Pemeriksaan oleh Dosen

Dosen cukup memeriksa empat hal berikut per pasangan kelompok:

  1. Tag ada dan waktunya sesuai batas.
  2. Commit setelah tag di branch freeze seluruhnya merujuk issue.
  3. Formulir serah-terima tersedia dan berstatus DITERIMA.
  4. Issue dibuka oleh penguji dan ditutup setelah retest.
# waktu pembuatan tag git for-each-ref refs/tags/v1.0-freeze --format='%(taggerdate:iso)' # daftar commit setelah freeze di branch freeze (tiap pesan harus menyebut issue) git log v1.0-freeze..origin/freeze --oneline # jumlah commit pada branch main setelah tag (informasi, bukan pelanggaran) git log v1.0-freeze..origin/main --oneline

Pemeriksaan ini bisa dilakukan di akhir sesi 12 (tag dan formulir) dan di sesi 14 (riwayat commit dan penutupan issue).

9 — Keterlambatan

Jika Freeze Terlambat

Keterlambatan pembangun juga merugikan kelompok penguji karena waktu pengujiannya berkurang. Karena itu konsekuensinya mencakup kedua sisi.

KeterlambatanDampak pada pembangunDampak pada penguji
Sampai 1 hariPeringatan tertulisTidak ada
2–3 hariPengurangan nilai komponen "Respons terhadap bug report"Cakupan pengujian dinilai proporsional terhadap waktu efektif yang tersedia
Lebih dari 3 hariDosen memutuskan tindak lanjutBoleh menguji berdasarkan dokumentasi yang ada; dosen memutuskan penyesuaian jadwal
Catatan

Angka pada tabel di atas adalah usulan awal. Dosen menyesuaikannya dengan kondisi kelas sebelum diumumkan ke mahasiswa.

Selama menunggu freeze, penguji tidak diam: mereka menyusun test plan dari dokumentasi yang sudah ada dan menyiapkan tools.

10 — Ringkas

Checklist Ringkas

Kelompok pembangun

  • Pra-freeze check diserahkan di sesi 11
  • Tag v1.0-freeze dibuat dan branch freeze menjadi sumber deployment
  • Paket serah-terima lengkap, termasuk kredensial dan data uji
  • Setiap perbaikan setelah freeze merujuk issue

Kelompok penguji

  • Smoke test dijalankan dan formulir serah-terima diisi
  • Bug dilaporkan memakai templat issue
  • Retest dilakukan sebelum issue ditutup
  • Jadwal dan skala uji beban disepakati dengan pembangun

Dosen

  • Batas waktu freeze dan batas perbaikan paket diumumkan
  • Tag, commit, formulir, dan issue diperiksa per pasangan
  • Aturan keterlambatan diumumkan sebelum sesi 11
